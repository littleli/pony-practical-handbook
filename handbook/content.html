The central question

For each reference, ask: what may I do through it, and what other references are allowed to exist? Pony checks both. Most capability errors become understandable once you name the alias that a line would create.

01 · Start with an ordinary mutable object

The notebook has a title and a growing list of notes. Main is an actor because a Pony executable starts there; the notebook itself is an ordinary class. Using Pony does not require turning every object into an actor.

{{example:01-local}}

Expected output: Pony lab: 1

Read the unfamiliar syntax once

  • class Notebook: a concrete object type. Pony has no class inheritance; reuse and abstraction use composition, traits and interfaces.
  • let title: String: initialize the field once. The title’s type is immutable String val; the standard String type defaults to val.
  • let _notes: Array[String]: a fixed field binding to a mutable array. The underscore makes the field private to this type. let does not freeze the array.
  • new create: a named constructor. title' is just a legal parameter name, pronounced “title prime.” All fields must be initialized.
  • fun ref add: a synchronous method that needs mutable access to its receiver, this.
  • fun box size(): USize: a synchronous method that reads its receiver. The last expression supplies its return value. USize is an unsigned machine-sized integer.
  • env.out.print: send an output message using the output stream supplied by the runtime.

book and same_book identify the same object. Calling add through either reference changes the array that size reads. This is aliasing, exactly as two Java variables can point to one object. The ref annotations make that intent explicit.

Java / Kotlin bridge

Pony let resembles Java final or Kotlin val on a binding. Pony val, the reference capability, is a different word in a different role: it promises immutable access with no writable aliases. Keep “can I reassign this variable?” separate from “can this object change?”

Exercise 1 · Add a second note through book. What prints?

Insert book.add("Understand aliases") before the print. The result is Pony lab: 2. Both references see the same notebook. Replacing let book with var book would permit rebinding the variable, but is unnecessary for mutating the object.

02 · Separate the object type from the reference type

Read Array[String val] ref from the inside out: each element is a String usable as val; the outer object is an Array usable as ref. These are two independent capability positions. Array[String] val changes the array’s capability. Array[String ref] ref instead describes an array of mutable String references.

Two checks for every value

Does the value provide the required type or methods? Does this reference provide the required access and alias guarantees? Having a method named add does not make it callable through box.

Nominal and structural contracts

A Pony trait requires a declared relationship, such as class Notebook is Named. A Pony interface can be satisfied structurally: having compatible methods is enough. Unlike a Java interface, the caller can use a Pony interface that the implementer did not explicitly name. Traits and interfaces can also provide default methods; adopting defaults requires the declared relationship.

Notebook declares Named. It satisfies Counted because its size method has the right signature. Describe is a primitive: a fieldless singleton, useful for stateless utility methods or marker values. Describe(book) invokes its apply method. Tuple positions use ._1, ._2, and so on.

Absence and partial operations are different

first() returns a union that explicitly represents absence. Array lookup _notes(0)? is a partial operation: it can raise Pony’s error when the index is invalid. The try … else … end converts that possibility into None. A match then handles the alternatives.

The ? at a call site means “this operation may raise an error.” It is not Kotlin’s nullable-type suffix or safe-call operator. To propagate an error, mark the enclosing fun partial too, with ? after its result type. Pony’s error carries no Java-style exception object; if callers need failure details, model a result union with data. A try without else handles an error by producing None.

03 · The six capabilities, as design choices

A capability belongs to a reference. The same object can be reached through different compatible reference capabilities. “This object is box” is usually less precise than “this reference is box.” The stronger promise of val comes from what it guarantees about all writable aliases.

Why control aliases at all? Suppose one actor mutates an array while another reads its elements. Giving only the second actor a read-only interface does not stop the first actor changing the array concurrently. Pony must control what other actors can access, not just what the current reference can call.

CapabilityThrough this referenceOther access that can coexistTypical choice
refRead and writeLocal readers and writers; no other actor can read/write this mutable stateYour actor’s ordinary working objects
boxReadMay coexist with a local writer; may instead view immutable dataA synchronous reader method or parameter
valReadOther readers, including other actors; no writable aliasConfiguration, published results, immutable messages
isoRead and write under isolation rulesIdentity-only aliases; no other readable/writable alias to the isolated objectA mutable parcel whose ownership moves
trnRead and write as the unique writerLocal read-only aliases; no other writer and no reader in another actorA builder that will become immutable
tagIdentity; tag methods; actor message sendsMakes no read/write guarantee about other referencesAn actor address or opaque identity

Sendable capabilities: iso, val, tag. A named iso must be moved when sending it. trn, ref and box cannot be behavior parameter capabilities. This is why “but my function only reads it” is insufficient at an actor boundary.

tag does not mean “useless object.” You can send a behavior message to an actor through tag. You can also call a fun tag method, whose implementation cannot inspect receiver fields. You cannot call an ordinary field-reading fun box method through it.

val protects the readable object graph, not just the outer binding. Opaque tag references inside an immutable object can still identify mutable actors; sending those actors messages does not turn the immutable object’s own state mutable.

Choose from the job, not from the error message

04 · A read-only view is not a frozen object

There are three capability positions in fun box notes(): Array[String] box. The first box is the capability required for this. The final box describes the returned array reference. Each String element defaults to val. Read each position separately.

{{example:03-views}}

Expected output: 1, then 2.

view cannot call add, but it observes changes made through book. editable_notes() explicitly exposes a mutable alias; this is legal locally, though a real API might keep mutation behind add to protect its invariants. This method is here to make the distinction visible.

Why the getter cannot return ref from a box receiver

Inside fun box notes, this is only readable. Although the field is declared Array[String] ref, reading it through that receiver gives a box view. Otherwise a caller could obtain mutable access through a read-only notebook. This combination of receiver capability and field capability is viewpoint adaptation.

Origin referenceA declared ref field is seen asReason
refrefLocal mutable access is available.
boxboxA readable origin must not expose a writer.
valvalThe readable state is immutable.
trnboxDo not leak a second writer.
isotagDo not leak a reader or writer from the isolated graph.
tagNo field accessOnly identity access is available.

This table is specifically about a ref field. A val field stays readable as val from readable origins, including iso. Also distinguish adapting a field access from storing a new alias to an iso field: storage must preserve alias guarantees too.

Useful defaults, and a reason to annotate

A plain fun defaults to a box receiver; an omitted result type defaults to None. An ordinary class type defaults to ref, unless the declaration gives a different default. Actors default to tag, primitives to val, and String declares a val default. Constructor expressions can also benefit from recovery: an inferred local initialized with a constructor is not guaranteed to be ref. In this compiler, several unannotated Notebook locals inferred as iso. Writing let book: Notebook ref = Notebook makes the intended local-aliasing design explicit.

05 · Copying a reference and moving a reference

When a named value is assigned, passed as an argument, or used as a method receiver, ask what reference the new name would hold. Ordinary ref, val, box and tag references can produce aliases with their own capability. Unique references require more care.

// Deliberately broken: two isolated owners would exist.
let parcel: Array[String] iso = recover iso Array[String] end
let second: Array[String] iso = parcel

Corrected version, starting from the same fresh parcel:

let parcel: Array[String] iso = recover iso Array[String] end
let second: Array[String] iso = consume parcel
// parcel cannot be read now. second owns the isolated reference.

consume invalidates the old local or parameter binding and yields its value. It neither copies the array nor destroys it. A consumed var can be assigned a new value before reuse; an existing alias is not erased by consuming a different variable.

Named referenceSafe ordinary alias capabilityWhat moving changes
isotagMoving can preserve iso or give up uniqueness to choose another capability.
trnboxMoving the unique writer can freeze to val, or become ordinary ref.
ref / val / box / tagThe same capabilityConsuming one name does not prove other aliases absent.

Read ^ and ! without mysticism

Array[String] iso^ is an ephemeral expression type: the isolated value is being handed over, rather than accessed through a retained name. consume parcel produces that kind of value. Storing it in let second: Array[String] iso gives it a new owner; second is now a named iso again. The caret is not a seventh capability and not an allocation operation.

A! means the safe alias type of generic type A. If A is iso, its alias capability is tag; if A is trn, box. This appears in generic collection signatures, because reading an element must not duplicate a unique owner.

A small, useful subtyping picture

ref ──→ box ──→ tag
val ──→ box ──→ tag

Moving iso^ can supply any of the six capabilities.
Moving trn^ can become val or ref (and their weaker views).

The arrows mean “can satisfy a requirement for,” not “automatically mutate the variable’s declared type.” Do not add an arrow from ref to val: having a writer tells the compiler nothing about other writers. consume ref_variable still cannot freeze an arbitrarily aliased object.

There is a further distinction between creating a lasting alias and temporary receiver access. Some calls such as parcel.push("note") are legal through iso because the compiler can recover the receiver after the call. Sendable arguments and a safe or unused result matter. If a call fails, inspect the full signature; do not conclude that iso objects cannot be mutated.

Exercise 5 · Why does consuming a ref not make it immutable?

Another variable may still hold a mutable reference. Consuming one name does not invalidate that other name. Starting with iso or trn supplies the missing uniqueness guarantee; creating a fresh graph inside recover is the other common route.

06 · Publish a snapshot without freezing your working state

The notebook stays mutable. A snapshot is a different array, populated with the same immutable String values. You can continue editing the notebook after taking it. This is often the most comfortable design for small programs: use local mutable state, publish stable results.

{{example:04-freeze}}

Expected output: 1, then 1.

Trace the snapshot’s references

  1. recover trn Array[String] end creates a fresh array and returns a write-unique reference.
  2. The loop reads the notebook’s local array through the box receiver. Each element is an immutable String and can be shared into the new array.
  3. result.push(note) fills the new array. Only result can write to it.
  4. consume val result gives up the unique writer and returns an immutable array. The notebook’s original array is unaffected.

If the element type were a mutable Note ref, reusing those references would not produce a deeply immutable snapshot. You would need immutable note objects, a conversion that builds immutable copies, or another ownership design. Changing the outer Array capability cannot repair mutable aliases inside it.

What recover proves

The second block constructs its entire array inside recover val … end, mutates it locally, then returns it as immutable. Mutable aliases created inside the region cannot escape as writers to the result. Captures from outside are restricted: arbitrary ref and box references cannot simply be pulled into the region and relabeled. Sendable captures are the normal allowed inputs; any iso input must still obey move rules.

Think of recover as a scope in which the compiler can establish stronger guarantees. It is not a runtime lock, a deep-copy request, a cast, or exception recovery. In this example, allocation and copying happen because we explicitly create another array and loop over the strings.

// Deliberately broken: an outer writer may still exist.
let notes: Array[String] ref = Array[String]
let frozen: Array[String] val = recover val notes end

The snapshot method deliberately allocates its trn result in a tiny recover region, then fills it outside that region. That lets the loop read the notebook’s non-sendable local state while only copying sendable Strings. Another valid design would perform the whole build inside recover if all required inputs were already sendable.

Exercise 6 · Make two snapshots around an edit. What sizes should they have?

07 · A message is an ownership boundary

A fun call runs synchronously. A be call enqueues a behavior for execution by the receiving actor. Other actors may execute at the same time, so message arguments must be sendable. The receiver runs one behavior at a time, which makes its own mutable state a natural place for ordinary ref objects.

{{example:05-transfer}}

Expected output: 2.

archive is an actor address, Archivist tag. The sender builds a mutable parcel, then consume parcel relinquishes access when sending it. The receiving behavior gets the isolated reference. It then consumes that iso into a local ref, deliberately giving up the need to transfer this particular array again. Ordinary local methods become straightforward.

The behavior’s body produces no synchronous calculated result for the caller. To return a result from a worker, send a message back to a reply actor. Do not write code that assumes the statement after a behavior call runs after the behavior completes.

Three message shapes worth memorizing

Message argumentSender’s actionUseful when
Array[String] valPass it normally; keep reading or send againMany actors need the same stable result
Array[String] isoMove a named parcel with consumeOne receiver should own mutable work
Worker tagPass the actor address normallyAnother actor needs to send it messages

box is not a substitute for val here. A local writer could still exist. trn is not a substitute for iso: its local box aliases could keep reading after the receiver began writing. Freeze the trn value to val before sharing it.

Reference capability versus object capability

The suffix tag controls access to a reference. The OutStream object itself grants the practical ability to send output. Passing env.out to Archivist gives that actor output authority. These are related security ideas but different uses of the word “capability.” Passing the narrow dependency also resembles constructor injection in Java.

Exercise 7 · Send the same result to two actors. Which representation fits?

Use Array[String] val and change the receiving behavior to take val. Both calls can use the same variable. Sending an iso twice would require creating two independent parcels or receiving the first one back before transferring it again.

08 · Read a generic signature in layers

A generic definition must be valid for every type and capability allowed by its bound. Java-style intuition about T as an unrestricted copyable object reference will get you stuck when A might be an iso value. Begin with the narrow set of capabilities your abstraction actually needs.

{{example:06-generics}}

Expected output: 1, then Pony lab.

Decode Slot

A: Any #read admits types with ref, val or box capability. Each can be aliased without duplicating a unique writer. The constructor can store the argument in _value. The box getter cannot blindly return A unchanged, because A might be a mutable reference and the Slot might only be readable.

this->A means “A as seen through the actual receiver’s viewpoint.” For a Slot[Notebook ref] ref, the getter can provide Notebook ref. For a Slot[Notebook ref] box, it provides Notebook box. For the immutable String value, it provides String val. The annotation let read: Notebook box in this example deliberately accepts the weaker view even though the mutable slot can provide ref.

An arrow is a type-level viewpoint operation, not a pointer dereference or a function-return arrow. In a generic container it keeps the result tied to the access the caller actually has. If an API should always hide mutation, use an explicitly box result for that concrete API, as Notebook.notes() does; a viewpoint-dependent result may intentionally expose ref to a ref caller.

ConstraintAccepted capability setDesign intent
A: Any valvalImmutable values only
A: Any #readref, val, boxValues usable through ordinary readable views
A: Any #sendiso, val, tagMessage-safe values; iso still needs moves
A: Any #shareval, tagValues that can be shared repeatedly
A: Any #any or unconstrained AAll sixMust handle uniqueness and opacity too

#read is the name of a capability set, not a promise that every other capability is unreadable. Iso and trn support reads under their uniqueness rules, but they are deliberately outside this set. The qualifiers are compile-time bounds, not seventh or eighth reference capabilities.

Why a completely generic getter gets harder

// Deliberately broken when A is unrestricted.
class Slot[A]
  let _value: A
  new create(value: A) => _value = consume value
  fun box get(): A => _value

If A could be iso, returning it as another iso would duplicate the owner. Adding this-> addresses viewpoints, but you must also account for aliasing of unique values. Signatures such as this->A! express an adapted safe alias, rather than promising to hand back another owner. Supporting an iso container may require a take/remove operation using destructive read rather than a conventional getter.

When reading standard-library methods, identify the receiver first, then the element type, then any ->, ! or ^, then ?. Many daunting signatures are just those four rules layered together. Avoid writing a maximally generic abstraction until you have two concrete uses that require it.

Exercise 8 · What changes if Slot.get is called through a box slot?

09 · Two patterns for the remaining sharp edges

Return to this chapter when the earlier stages feel comfortable. These patterns explain why trn exists and how to hand out a unique value stored in a field.

{{example:07-trn-and-drain}}

Expected output: 1, 1, 1, 0.

One writer, then no writers

draft is trn: it is the only writer. view is a legal local box alias. consume val draft relinquishes the writer and creates an immutable reference. The existing box view remains safe: it never promised the object would remain mutable. It can still read the now-frozen state.

This explains a practical difference from iso. If draft were iso, retaining a readable view would break isolation. Trn is useful when local readers should coexist with construction, while preserving a future freeze operation. Most small programs can introduce trn only at that point.

Move a field by replacing it

consume works on locals and parameters, not on fields: leaving a field empty would be unsafe if the containing object were accessed through another alias. Pony assignment instead evaluates to the previous value of its left side. In drain, the field receives a fresh empty iso array, and the old iso array is returned as an ephemeral result.

fun ref drain(): Array[String] iso^ =>
  _pending = recover iso Array[String] end

The field always has a value. The first drain returns the queued note. The second returns an empty array. Returning _pending without replacing it would try to create a second isolated owner. This pattern is called destructive read; it transfers the old reference without destroying the array.

The assignment rule also matters in mundane setters. If a method explicitly returns a value and its last expression is field = new_value, it returns the old value. Write an explicit final expression when you intend another result.

Exercise 9 · Why does drain require a ref receiver?

It replaces _pending, so it must mutate the Outbox. A box receiver cannot do that. A method that merely reports the count could use box, subject to the field’s viewpoint and access rules.

References: Destructive read, Trn guarantees.

10 · A complete command-line notes program

This stage takes command-line arguments as notes, builds mutable state locally, freezes a snapshot, and sends it to a Printer actor. The extra actor exists to exercise the message boundary; a production tool this small could print directly from Main.

{{example:08-notes-cli}} 
ponyc examples/08-notes-cli -o .build -b notes
./.build/notes "learn views" "move a parcel"

# Total: 2

use "collections" brings in Range. The first command-line argument is the executable name, so Range[USize].till(1, env.args.size()) starts at 1 and excludes env.args.size(). Pony 0.78 uses the named constructor till for an exclusive far bound. Array lookup remains partial even though the loop bounds are sensible: the compiler does not prove that arbitrary index arithmetic is in bounds. Here, the empty try handler skips an unexpected lookup failure; for user input parsing, report invalid data explicitly instead of silently dropping it.

The ownership review you should be able to give

  1. book: Notebook ref is local working state. It needs mutation and ordinary local aliases.
  2. _notes: Array[String] ref is private mutable storage. Its immutable String elements can be reused in snapshots.
  3. snapshot() has a box receiver because reading the notebook is enough. It allocates a separate array.
  4. result is trn while built, then consumed into val. No writer to the result survives.
  5. Printer receives Array[String] val. Main may keep that snapshot because it cannot race a writer.
  6. _out: OutStream is an actor reference. Printer sends output messages through it.

Three small extensions

A · Print numbered notes

Inside Printer.show, start a var index: USize = 1, print index.string() + ". " + note, then increment it. The counter is local mutable state. The notes stay val.

B · Add a title without changing the ownership design

Add let title: String and a constructor parameter to Notebook. Pass title as a separate immutable String argument to Printer.show. No additional capability machinery is needed. This is a useful test of whether you can change functionality without randomly changing ownership.

C · Give the printer mutable ownership instead

Change the message parameter to Array[String] iso. Build an iso parcel separately, move it with consume, and consume it into a local ref in Printer as in stage 05. The sender must stop using that parcel. Keeping the original mutable notebook is fine if the parcel contains a separate copied array of immutable Strings.

You are ready to build small programs when you can recreate this structure from an empty directory and explain the six ownership decisions above. Memorizing the full capability matrix is a less useful milestone.

11 · Repair the violated guarantee

Read a capability diagnostic from the immediate mismatch outward. Write down the actual expression type, the required type, and whether this line stores an alias, moves a value, calls a method, accesses a field, or crosses an actor boundary. Then choose a repair that preserves the program’s intent.

A repair order that saves time

Check the concrete type and numeric type first. Then check the receiver capability. Then check viewpoint adaptation and aliasing. Only then decide whether the design needs a move, a snapshot, or another ownership boundary.

Each case below is a separate deliberately broken package in failures/. The diagnostics are captured from the installed compiler. The verifier checks the intended reason as well as the nonzero exit code. Fix cases in a copy so that the original rejection checks remain reproducible.

{{failure:01-box-write}}

Reason: the call requires a mutable receiver but view supplies box. Repair: call through the existing book ref. If this API should permit mutation, give its caller a ref deliberately. Adding consume to a box reference cannot manufacture write access.

{{failure:02-iso-alias}}

Reason: ordinary assignment would retain the original isolated owner and introduce another. Repair: initialize second with consume parcel. If only identity is needed, use a tag alias. If both names must read the content, publish val instead.

{{failure:03-send-ref}}

Reason: a behavior parameter must cross an actor boundary safely. Ref permits local writers and readers. Repair: choose a val snapshot or an iso ownership transfer, then update the sender to construct that representation. Changing only the declaration to box still fails.

{{failure:04-freeze-ref}}

Reason: consume removes one binding, not other potential writers. Repair: build immutable data in recover, copy into a snapshot, or start with iso/trn when uniqueness is part of the intended lifecycle. Do not treat a capability annotation as a cast.

{{failure:05-use-after-consume}}

Reason: the old binding has been invalidated. Repair: use the new owner, compute the required summary before moving, or redesign around immutable shared data. The old object still exists; the old name cannot access it.

{{failure:06-leaking-getter}}

Reason: a ref field seen through a box receiver is box. Repair: return Array[String] box for a read-only API. Use a ref receiver for an intentionally mutable accessor, or return an independent val snapshot.

{{failure:07-generic-getter}}

Reason: unrestricted A can include unique capabilities, and a box receiver also affects the field’s viewpoint. Repair: use the chapter 08 #read bound plus this->A if those are the intended inputs. A genuinely unrestricted container needs explicit alias/move handling.

{{failure:08-recover-capture}}

Reason: the region tries to turn an external mutable reference into val. The diagnostic shows that the captured value is only available here as tag, which cannot be recovered into a readable immutable reference. Repair: allocate the graph inside recover, or copy sendable values into a new iso/trn builder as the snapshot method does. Wrapping the existing writer in recover does not establish isolation.

12 · Keep this beside your editor

Start with these defaults in your own designs

  • Local working object: T ref.
  • Synchronous method that only reads its receiver: fun box.
  • Method that mutates its receiver: fun ref.
  • Read-only local input: T box; it need not be permanently frozen.
  • Stable data that must be sent or retained by several actors: T val.
  • Mutable data whose ownership must move: T iso, then consume a named owner at transfer.
  • A single writer whose result will be frozen: T trn, then consume val.
  • Actor address: Worker tag.

Design before annotation

Draw one box for each actor. Put mutable working objects inside their owning actor. For every arrow between actors, decide whether it carries shared immutable data, a moved mutable parcel, or an actor address. Only then write the capability suffixes. If a single value needs contradictory properties, split working state from published results.

  8. Why must moving a field also replace its value?
Answers in eight sentences
  1. Let fixes the binding; the reference capability controls object access.
  2. Ref supplies read access; box supplies no proof that writers are absent.
  3. It attempts a second isolated readable/writable owner while retaining the first.
  4. It invalidates that local or parameter binding; the object and any permitted other aliases survive.
  5. A read-only origin cannot grant mutable access through its fields.
  6. Val forbids writers and iso transfers the owner; box can coexist with a local writer.
  7. It adapts the returned type to the actual receiver’s viewpoint.
  8. Another alias might access the containing object, so the field must never be empty.

The useful habit is to tell a short ownership story for your program. The compiler then checks that your code keeps the promises in that story.
